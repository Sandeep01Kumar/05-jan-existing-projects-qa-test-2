## Description

This epic validates that the Firebase Crashlytics SDK is correctly capturing, uploading, and surfacing crashes on every client platform (Android, iOS, Flutter, Unity, React Native) BEFORE the legacy Fabric SDK is decommissioned by `EPIC-MIG-10`. Validation is performed by forcing test crashes through platform-idiomatic APIs — on Android `throw RuntimeException("Force Crash")` (Kotlin) or `throw new RuntimeException("Force Crash")` (Java), on iOS `fatalError("Force Crash")` in Swift or `[NSException raise:...]` in Objective-C, with framework-specific equivalents for Flutter (`FirebaseCrashlytics.instance.crash()`), Unity (the Firebase Unity test-crash API), and React Native (`crashlytics().crash()`) — and confirming receipt of the resulting crash report in the Firebase Console under `DevOps & Engagement → Crashlytics` within the canonical 5-minute visibility window after cold relaunch of the crashed app. A dual-running validation window operates with BOTH the Fabric SDK and the Firebase Crashlytics SDK active in production for a minimum of 7 consecutive days of production traffic, which allows the release manager to compare crash volume, crash-free-users metric, and top-issue fingerprints between the two reporters and detect any silent regression before the legacy SDK is removed. This epic is the GATE between the platform SDK swap epics (`EPIC-MIG-03`, `EPIC-MIG-04`, `EPIC-MIG-05` — Phase 2) plus data reconciliation (`EPIC-MIG-08` — Phase 4) and the terminal decommission epic (`EPIC-MIG-10` — Phase 6); its terminal artifact, the cutover sign-off, is the auditable authorization that releases `EPIC-MIG-10` to begin.

## Business Value

Test-crash validation eliminates the risk of silent crash-collection failure post-cutover by producing an objective, observable signal — a forced crash arrives in the Firebase Console within 5 minutes of cold relaunch, or it does not — that the migration program can stake its decommission decision on. The dual-running validation window is the migration program's safety net: with both Fabric and Firebase Crashlytics SDKs reporting in parallel for a minimum 7-day window, if Firebase crash volume is materially lower than Fabric for the same time period and the same device population, the team can pause and investigate WITHOUT having already decommissioned Fabric and thereby lost the legacy diagnostic baseline. The canonical 5-minute Firebase Console visibility window from public Firebase troubleshooting guidance gives the validation team a tight, objective criterion that does not require subjective judgment, making the validation deterministic rather than aspirational. The validation gate produces a verifiable, auditable cutover sign-off artifact that satisfies release management, engineering, and security stakeholder requirements before decommission and that downstream audit reviewers can independently inspect to confirm the migration was validated rather than merely executed. Roles that benefit include mobile developers (objective per-platform confirmation that the new SDK works end-to-end before they commit to removing the legacy one), release managers (a dual-running comparison window that protects the release-quality signal during the transition), on-call engineers (confidence that crash reports will still arrive after cutover so paging behavior remains reliable), the migration program lead (a hard, evidence-backed entry gate to decommission rather than a calendar-driven one), and security/audit reviewers (a signed-off artifact that records who approved the cutover and against what evidence).

## In Scope

The following items are included in this epic:

- Implementation of a debug-only "Force Crash" affordance (typically a button on a hidden developer screen, gated by a debug-only feature flag) in each client app (Android, iOS, Flutter, Unity, React Native) that invokes the platform-idiomatic test-crash API and is wrapped so it cannot ship to end-user release channels.
- Forced test-crash execution on a release-mode (or release-equivalent) build of each client platform in scope, exercising the same code-signing, obfuscation, and packaging path that real production builds use so the validation reflects the production crash-reporting pathway and not a debug-only one.
- Verification that each platform's test crash appears in the Firebase Console Crashlytics dashboard (navigated via `DevOps & Engagement → Crashlytics`) within the canonical 5-minute visibility window from cold relaunch of the crashed app, with the report card showing device details, app version, OS version, device model, and a symbolicated stack trace whose frames reference original source-level identifiers (per `EPIC-MIG-06` symbol and mapping upload cutover) rather than hex addresses or obfuscated tokens.
- Operation of a dual-running validation window in which both the legacy Fabric SDK and the new Firebase Crashlytics SDK are active in production simultaneously, reporting crashes for the same set of devices and the same app version for a minimum of 7 consecutive days of production traffic so that statistically meaningful parity comparison is possible.
- Parity comparison of crash volume, crash-free-users metric, and top-issue stack-trace fingerprint lists between the Fabric and Firebase consoles during the dual-running window, with the comparison interpreted against the reconciliation baseline produced by `EPIC-MIG-08` and against the canonical Firebase guidance that the new SDK is estimated to capture about 30% more Android crashes than the legacy Fabric SDK (so a positive Firebase delta is expected and is not, by itself, a regression signal).
- Documentation of any dual-running anomaly (for example, Firebase volume substantially below Fabric volume, an issue tracked in Fabric disappearing from Firebase, or a fingerprint divergence on a high-volume issue) with a root-cause analysis attached to the cutover sign-off artifact; anomalies are either resolved before sign-off or explicitly accepted as a named, owner-attributed known risk.
- Production of the cutover sign-off artifact — a markdown document committed to the migration program documentation — that captures per-platform test-crash receipt confirmation, dual-running parity results, the reconciliation baseline from `EPIC-MIG-08`, any anomalies and their resolutions, and explicit signatures from release management, engineering, and security stakeholders that authorize `EPIC-MIG-10` decommission to begin.
- Documentation of the Crashlytics debug logging procedure (Android: `adb shell setprop log.tag.FirebaseCrashlytics DEBUG`; iOS: setting the `-FIRDebugEnabled` launch argument) for diagnosing the scenario in which a forced test crash does not appear in the Firebase Console within 5 minutes, so that the validation team has a reproducible diagnostic step rather than an unstructured triage path.

## Out of Scope

The following items are explicitly excluded from this epic and are typically owned by a sibling or successor epic:

- The actual removal of Fabric SDK references from client code and CI, the retirement of legacy Fabric symbol- and mapping-upload jobs, and the archival of the Fabric organization itself — owned by `EPIC-MIG-10` (Fabric SDK decommission). This epic produces the cutover sign-off artifact that AUTHORIZES `EPIC-MIG-10` to begin, but does not itself perform any decommission step.
- Historical Crashlytics data migration via the Firebase migration page and pre/post-cutover issue count reconciliation — owned by `EPIC-MIG-08` (historical data migration). This epic CONSUMES the reconciliation baseline produced by `EPIC-MIG-08` to interpret dual-running parity but does not itself migrate or reconcile historical data.
- SDK installation, build-system integration, and initialization changes for any client platform — owned by `EPIC-MIG-03` (Android), `EPIC-MIG-04` (iOS), and `EPIC-MIG-05` (Flutter, Unity, React Native). This epic VALIDATES the SDKs those epics installed; integration defects discovered during validation are referred back to the appropriate predecessor epic rather than fixed here.
- Symbol and mapping upload pipeline cutover (Android ProGuard/R8 mapping upload, iOS dSYM upload, NDK native symbol upload) — owned by `EPIC-MIG-06`. This epic CONSUMES symbolicated stack traces produced by `EPIC-MIG-06`'s upload pipeline; if symbolication is incomplete or broken when a test crash arrives in the Firebase Console, the defect is referred back to `EPIC-MIG-06` rather than treated as a Phase 5 validation failure.
- Translation of Fabric Answers events to Google Analytics for Firebase predefined or custom events — owned by `EPIC-MIG-07`. Breadcrumb logs that appear on Firebase Crashlytics issue cards during this epic's validation are produced by `EPIC-MIG-07`'s translation work; any breadcrumb-related gaps are referred back to that epic.

## User Stories

This epic contains 4 user stories. Each story is derived from `../templates/story-template.md` and embedded inline below using H3 headings (Rule AR-1). Stories live INSIDE their parent epic file to keep each epic self-contained and eliminate broken cross-file links during refactors. The four stories are intentionally partitioned so that the two highest-volume native platforms (Android in `STORY-MIG-09-S01` and iOS in `STORY-MIG-09-S02`) each receive a dedicated story; cross-platform validation (Flutter, Unity, React Native) is covered by the epic-level acceptance criteria and Definition of Done bullets because those platforms use the same Firebase Console verification pathway and the same 5-minute visibility window, differing only in the test-crash API invocation idiom owned by their respective installation epics (`EPIC-MIG-05`).

### STORY-MIG-09-S01: Force a test crash on Android and confirm receipt

**As a** mobile developer, **I want** to force a test crash on a release-mode Android build and confirm receipt in the Firebase Console, **so that** I can verify the Firebase Crashlytics SDK installed by `EPIC-MIG-03` is correctly capturing and uploading crashes from Android before the legacy Fabric SDK is decommissioned by `EPIC-MIG-10`.

#### Acceptance Criteria

- **Given** a release-mode Android build with the Firebase Crashlytics SDK integrated (per `EPIC-MIG-03`) and the ProGuard/R8 mapping file uploaded (per `EPIC-MIG-06`), **When** the test user triggers the debug-gated "Force Crash" button which executes `throw RuntimeException("Force Crash")` (Kotlin) or `throw new RuntimeException("Force Crash")` (Java), **Then** the app terminates with a non-zero exit code and the unhandled exception is intercepted by the Firebase Crashlytics SDK's uncaught-exception handler rather than by any third-party global handler.
- **Given** the app has crashed and been cold-relaunched (so the buffered crash report can upload on next launch per the canonical Firebase Crashlytics ingestion model), **When** the developer opens the Firebase Console under `DevOps & Engagement → Crashlytics` for the corresponding Firebase project (provisioned by `EPIC-MIG-02`), **Then** the test crash appears in the Crashlytics dashboard within 5 minutes of cold relaunch per the canonical Firebase troubleshooting guidance.
- **Given** the crash report card in the Firebase Console, **When** the developer expands it, **Then** the report includes device details (manufacturer and model), app version (matching the build that produced the crash), Android OS version, device name, and the originating bundle's `application_id` matches the package name registered in the Firebase project's Android app binding.
- **Given** the stack trace shown in the Firebase Console, **When** the developer reviews it, **Then** the trace is symbolicated against the uploaded mapping file so that the line number, class name, and method name corresponding to the `RuntimeException("Force Crash")` call site are visible in original (non-obfuscated) form rather than as `R8`-mangled tokens.

#### Notes

- If the test crash does not appear within 5 minutes, enable Crashlytics debug logging via `adb shell setprop log.tag.FirebaseCrashlytics DEBUG` and re-run the test; the device log should show the SDK serializing the crash report on the original crash, attempting upload on cold relaunch, and reporting either a successful upload or an explicit error reason. Persistent failure to upload after debug logging is enabled indicates an integration defect to refer back to `EPIC-MIG-03`.
- The "Force Crash" button must be wrapped in a debug-only feature flag (for example, `BuildConfig.DEBUG` gating, or a remote-config kill-switch that is OFF by default) so the affordance never ships to end-user release channels; the dual-running validation window in `STORY-MIG-09-S03` does not depend on user-triggered test crashes, only on naturally occurring production crashes, so the button can remain debug-only.

### STORY-MIG-09-S02: Force a test crash on iOS and confirm receipt

**As a** mobile developer, **I want** to force a test crash on a release-mode iOS build and confirm receipt in the Firebase Console, **so that** I can verify the Firebase Crashlytics SDK installed by `EPIC-MIG-04` is correctly capturing and uploading crashes from iOS before the legacy Fabric SDK is decommissioned by `EPIC-MIG-10`.

#### Acceptance Criteria

- **Given** a release-mode iOS build with the Firebase Crashlytics SDK integrated via CocoaPods or Swift Package Manager (per `EPIC-MIG-04`) and `FirebaseApp.configure()` called at app startup, **When** the test user triggers the debug-gated "Force Crash" button which executes `fatalError("Force Crash")` in Swift or `[[NSException exceptionWithName:@"ForceCrash" reason:@"Force Crash" userInfo:nil] raise]` in Objective-C, **Then** the app terminates abnormally with the iOS crash reporter receiving the signal (`SIGTRAP` for `fatalError`, `SIGABRT` for an uncaught `NSException`) and the Firebase Crashlytics SDK serializes the crash to its on-device buffer before process exit.
- **Given** the app has crashed and been cold-relaunched, **When** the developer opens the Firebase Console Crashlytics dashboard for the corresponding Firebase project, **Then** the test crash appears within 5 minutes of cold relaunch and is grouped under a new issue card whose first-seen timestamp matches the crash time.
- **Given** the dSYM files for the crashed build have been uploaded to Firebase per `EPIC-MIG-06` (whether via the bundled Firebase `upload-symbols` script, a CocoaPods/SPM Run Script Build Phase, or a `fastlane upload_symbols_to_crashlytics` action), **When** the developer reviews the stack trace in the Firebase Console, **Then** the trace is symbolicated with original Swift or Objective-C symbol names, source file paths, and line numbers rather than hex addresses or `__hidden#NNNNN` stripped tokens.
- **Given** the crash report card, **When** the developer expands it, **Then** iOS device details (device model, e.g., `iPhone15,3`), app version, iOS OS version, device name (if reported), and the originating bundle identifier are visible and the bundle identifier matches the iOS app registration in the Firebase project.

#### Notes

- On iOS, `fatalError()` in Swift produces a `SIGTRAP` whereas force-unwrapping a `nil` optional (`someOptional!`) produces a `SIGSEGV` via the Swift runtime; both crash classes are handled by the Firebase Crashlytics SDK's signal handlers, but exhaustive validation may exercise both idioms to confirm parity across signal types. For Objective-C codebases, an uncaught `NSException` raised via `[NSException raise:format:]` is a separate code path from a Mach signal and is also covered by the Crashlytics signal-and-exception handler chain.
- The dSYM upload from `EPIC-MIG-06` is a HARD prerequisite for symbolicated traces — without it, the test crash will still appear in the Firebase Console but stack frames will display hex addresses (e.g., `0x0000000104abcd12`) instead of symbolic names. If symbolication is missing despite the dSYM having been uploaded, verify in the Firebase Console under the issue card's `dSYMs` view that the upload was registered for the correct build UUID; the build UUID embedded in the binary must match the UUID of the uploaded dSYM bundle.

### STORY-MIG-09-S03: Operate dual-running validation window with parity comparison

**As a** release manager, **I want** to operate a validation window in which both the Fabric and Firebase Crashlytics SDKs are active in production simultaneously, **so that** I can compare crash volume parity between the two reporters against the reconciliation baseline produced by `EPIC-MIG-08` and detect any silent regression before authorizing `EPIC-MIG-10` to decommission the legacy SDK.

#### Acceptance Criteria

- **Given** a production release with both the Fabric SDK and the Firebase Crashlytics SDK active and initialized at app startup (per the platform-specific SDK swap epics), **When** the dual-running window is open, **Then** both SDKs report crashes for the same set of devices and the same app version, the Firebase Console Crashlytics dashboard receives production crash reports continuously, and the legacy Fabric console continues to receive production crash reports until decommission so the two consoles can be cross-compared.
- **Given** the dual-running window has accumulated a minimum of 7 consecutive days of production traffic (or the longer agreed window for higher-risk apps as documented during `EPIC-MIG-01` readiness), **When** the release manager queries crash volume in both consoles for the identical time window and identical app version, **Then** Firebase crash volume is within ±10% of Fabric crash volume after accounting for the canonical Firebase guidance that the new SDK is estimated to capture about 30% more Android crashes than the legacy Fabric SDK (so a positive Firebase delta of up to roughly +30% on Android, and within ±10% on iOS, is expected and is not flagged as a regression).
- **Given** the top-10 issues list in each console for the same comparison window, **When** the release manager compares them side by side, **Then** the highest-volume issues have overlapping stack-trace fingerprints across both reporters, no issue tracked by Fabric in the comparison window has disappeared from the Firebase top-issues list, and any issue that appears in Firebase but not Fabric is explainable by the documented +30% Android capture improvement or by a known fingerprint convergence and is recorded in the cutover sign-off artifact.
- **Given** any anomaly detected during the window (for example, Firebase volume substantially below Fabric for a specific device class, a Fabric-tracked issue absent from Firebase, or a fingerprint divergence on a high-volume issue), **When** the release manager investigates, **Then** a documented root-cause analysis is attached to the cutover sign-off artifact and the anomaly is either resolved (re-validating the affected platform) or explicitly accepted as a named, owner-attributed known risk that does not block sign-off.

#### Notes

- The 7-day minimum aligns with typical release-management practice for cross-validation and is intentionally framed as a MINIMUM duration rather than a calendar period (Rule AR-6 — no time-based planning). Higher-risk apps, apps with weekly traffic seasonality, or apps with low absolute crash volumes may extend the window — for example, low-volume apps may require 14 or 21 days for the parity comparison to be statistically meaningful. The actual window for each app is agreed during `EPIC-MIG-01` readiness based on the app's traffic profile.
- The +30% Android crash capture improvement is documented in the canonical Firebase Blog announcing the new SDK; the release manager should explicitly call out this expected positive delta in the cutover sign-off artifact so that downstream auditors do not mistake the higher Firebase volume for a Fabric regression. iOS volume is generally expected to be closer to parity because the legacy Fabric iOS SDK was less affected by the capture gaps that the new SDK closes on Android (ANR collection improvements, post-app-close upload behavior).

### STORY-MIG-09-S04: Produce cutover sign-off artifact gating EPIC-MIG-10

**As a** migration program lead, **I want** a formal, auditable cutover sign-off artifact that captures test-crash receipt evidence, dual-running parity results, and explicit stakeholder signatures, **so that** the decision to authorize `EPIC-MIG-10` (Fabric SDK decommission) is documented, evidence-backed, and independently inspectable by audit reviewers rather than being an implicit handoff.

#### Acceptance Criteria

- **Given** all three preceding stories (`STORY-MIG-09-S01`, `STORY-MIG-09-S02`, `STORY-MIG-09-S03`) have their acceptance criteria satisfied for every in-scope app on every in-scope platform, **When** the program lead drafts the cutover sign-off artifact, **Then** the artifact captures, in named subsections: (i) per-platform test-crash receipt confirmation (Android, iOS, Flutter, Unity, React Native — one row per in-scope app per platform), (ii) the dual-running window's parity results against the reconciliation baseline produced by `EPIC-MIG-08`, (iii) the canonical +30% Android capture allowance applied during interpretation, (iv) every anomaly observed during the window along with its resolution or named-risk acceptance, and (v) explicit sign-off signatures (named individuals) from release management, engineering, and security stakeholders.
- **Given** the cutover sign-off artifact is published to the migration program documentation and linked from the migration theme `README.md`'s Program Exit Criteria section, **When** the team responsible for `EPIC-MIG-10` checks the validation gate before commencing decommission, **Then** the artifact is reachable, all three sign-off signatures are present and dated, and the team can proceed with decommission knowing the validation gate is closed.
- **Given** any unresolved anomaly from the dual-running window remains open at the time the program lead drafts the sign-off, **When** the program lead reviews the draft, **Then** the artifact is HELD (not published) until the anomaly is either documented and resolved (re-validating the affected platform) OR explicitly accepted as a named, owner-attributed known risk by all three sign-off stakeholders; the artifact is never published with unresolved anomalies still in an open, un-owned state.
- **Given** any in-scope app's per-platform test-crash receipt cannot be confirmed (for example, the Firebase Console does not show the test crash within 5 minutes even after the debug logging procedure has been exhausted), **When** the program lead reviews the sign-off draft, **Then** that app is explicitly deferred from the sign-off and is recorded as a per-app exception with a remediation owner and a re-entry path back into validation, rather than being implicitly approved by silence.

#### Notes

- The sign-off artifact is itself a markdown document committed to the migration program documentation; it is not a separate ticketing-system record and not a slide deck, because the catalog convention (and the broader documentation-only scope of this migration program per the AAP) is markdown-first. The artifact should be linked from the migration theme `README.md`'s Program Exit Criteria section so the entry gate to `EPIC-MIG-10` is discoverable.
- A future iteration of the catalog may introduce a reusable sign-off-artifact template under `../templates/` (analogous to `epic-template.md` and `story-template.md`); for this migration, an ad-hoc but uniformly structured markdown document is sufficient and the convention of named subsections enumerated in the first acceptance criterion provides enough structure for downstream auditors.

## Acceptance Criteria (Epic-Level)

The following Given-When-Then criteria summarize exit conditions across all stories in this epic (Rule AR-4). They satisfy the user's R-2 directive ("epics with acceptance criteria") and are applied symmetrically with the pipeline theme for catalog uniformity. Per the AAP, this epic carries 5 epic-level acceptance criteria so that the gate to `EPIC-MIG-10` decommission is unambiguously specified.

- **Given** a release-mode (or release-equivalent) build of every client platform in scope (Android, iOS, Flutter, Unity, React Native), **When** a debug-gated force-crash is triggered through each platform's idiomatic test-crash API and the app is cold-relaunched, **Then** the resulting test crash is visible in the Firebase Console Crashlytics dashboard for the corresponding Firebase project within 5 minutes of cold relaunch, with the report card showing device details, app version, OS version, and a symbolicated stack trace.
- **Given** the dual-running validation window has elapsed (minimum 7 days of production traffic, or the longer agreed window for higher-risk apps), **When** the release manager queries crash volume in both the legacy Fabric console and the Firebase Crashlytics dashboard for the identical time window and identical app version, **Then** Firebase crash volume is within ±10% of Fabric volume on iOS and within +30%/−10% of Fabric volume on Android (allowing positive delta for the documented +30% Android capture improvement), and any deviation outside these bands is either resolved or accepted as a named known risk in the cutover sign-off artifact.
- **Given** the Firebase Console Crashlytics dashboard at the close of the dual-running window, **When** an on-call engineer reviews the top-issues list for each in-scope platform, **Then** at least one symbolicated stack trace is visible per platform — confirming that `EPIC-MIG-06` symbol and mapping uploads have produced human-readable stacks in production data rather than only against the synthetic test crashes from `STORY-MIG-09-S01` and `STORY-MIG-09-S02`.
- **Given** the cutover sign-off artifact is published and linked from the migration theme `README.md`'s Program Exit Criteria section, **When** an auditor inspects it, **Then** it contains per-platform test-crash receipt confirmation, dual-running parity results referenced against the reconciliation baseline from `EPIC-MIG-08`, every observed anomaly with its resolution or named-risk acceptance, and explicit named signatures from release management, engineering, and security stakeholders.
- **Given** all four embedded stories (`STORY-MIG-09-S01` through `STORY-MIG-09-S04`) have their acceptance criteria satisfied for every in-scope app and platform, **When** the migration program lead audits the epic against the readiness report from `EPIC-MIG-01` and the reconciliation baseline from `EPIC-MIG-08`, **Then** the gate to `EPIC-MIG-10` (Fabric SDK decommission) is declared open and the cutover sign-off artifact is the explicit entry criterion that `EPIC-MIG-10` references at its commencement.

- All 4 embedded stories (`STORY-MIG-09-S01`, `STORY-MIG-09-S02`, `STORY-MIG-09-S03`, `STORY-MIG-09-S04`) have their acceptance criteria satisfied for every in-scope app and platform.
- All 5 epic-level acceptance criteria above are satisfied.

- A debug-gated force-crash test on iOS produces a Firebase Console entry within 5 minutes of cold relaunch, with a symbolicated stack trace identifying the `fatalError("Force Crash")` (or `NSException` raise) call site in original (non-stripped) form.
- A debug-gated force-crash test on Flutter (`FirebaseCrashlytics.instance.crash()`), Unity (the Firebase Unity test-crash API), and React Native (`crashlytics().crash()`) each produces a Firebase Console entry within 5 minutes of cold relaunch, with timing parity to the native platforms.
- The dual-running validation window has elapsed with a minimum of 7 consecutive days of production traffic, and the parity comparison against the `EPIC-MIG-08` reconciliation baseline is documented inline in the cutover sign-off artifact with per-platform crash-volume figures.
- The cutover sign-off artifact is published to the migration program documentation, linked from the migration theme `README.md`'s Program Exit Criteria section, and signed by named individuals from release management, engineering, and security; no unresolved anomalies remain in an open, un-owned state.
- The Crashlytics debug logging procedure (Android `adb shell setprop log.tag.FirebaseCrashlytics DEBUG`, iOS `-FIRDebugEnabled`) is documented in the migration program documentation as a reproducible diagnostic step for the scenario in which a forced test crash does not appear within 5 minutes.
- The "Force Crash" affordance in every client app is verified to be debug-gated (for example, behind `BuildConfig.DEBUG` on Android, behind a `#if DEBUG` block on iOS) so it cannot ship to end-user release channels.
