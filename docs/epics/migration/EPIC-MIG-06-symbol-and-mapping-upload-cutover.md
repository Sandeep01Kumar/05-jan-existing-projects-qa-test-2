## Description

This epic cuts over the symbol- and mapping-upload pipelines from the legacy Fabric distribution to Firebase Crashlytics across three orthogonal artifact classes: Android ProGuard/R8 mapping files (covering Java and Kotlin obfuscation), iOS dSYM files (covering Swift and Objective-C symbolication on Apple platforms), and NDK native symbol files (covering C/C++ native code symbolication for Android apps that ship native libraries). Per the canonical Firebase Blog announcement, the new Firebase Crashlytics Gradle plugin is streamlined around a new API in `build.gradle` for managing and uploading mapping files and native symbol files, and the plugin's total size was reduced from over 20 MB to approximately 100 KB — a roughly 200x footprint reduction that materially lowers CI image size, Gradle dependency-resolution time, and developer-workstation download overhead. Mapping and symbol artifacts are a hard prerequisite for human-readable crash reports: per the Firebase Crashlytics documentation, Crashlytics uses mapping information for the app's build (for example, dSYM files for Apple platforms) to create human-readable crash reports — without these artifacts, the Firebase Console renders obfuscated tokens for Android (e.g., `a.b.c.d`) and hex addresses for iOS and NDK frames (e.g., `0x10004a2b8`), making crash triage impractical at any non-trivial scale. The epic updates the CI/CD pipelines of every in-scope client app so that release builds invoke the new Firebase upload commands (`./gradlew uploadCrashlyticsMappingFile<Variant>` for ProGuard/R8 mappings, `./gradlew uploadCrashlyticsSymbolFile<Variant>` for NDK native symbols, the Firebase-targeted Run Script Build Phase or `fastlane upload_symbols_to_crashlytics` action for iOS dSYMs) rather than the legacy Fabric upload commands, with explicit validation that symbolicated stack traces appear in the Firebase Console for at least one representative crash per platform. This epic depends on the platform SDK installations performed by `EPIC-MIG-03` (Android), `EPIC-MIG-04` (iOS), and `EPIC-MIG-05` (cross-platform); it precedes the historical data migration in `EPIC-MIG-08` because reconciliation of pre- and post-cutover issue counts is materially easier when stack traces are symbolicated on both sides.

## Business Value

Symbolicated stack traces are the difference between an actionable crash report and an unprioritizable opaque token — without them, mobile developers spend significant manual effort cross-referencing obfuscated identifiers against private mapping files, which scales poorly across release cadences and across the per-issue, per-version, per-device triage workload that crash reporting is designed to compress. The new Firebase Crashlytics Gradle plugin's footprint reduction (from over 20 MB to approximately 100 KB per the Firebase Blog) lowers CI image size and reduces the per-build cold-cache download time, materially shortening the legacy Fabric plugin's drag on CI throughput. The plugin's streamlined `build.gradle` API simplifies CI/CD pipeline maintenance by replacing the legacy Fabric configuration (which required `fabric.io` credentials, a Run Script Build Phase, and per-target plumbing) with conventional Gradle tasks that integrate with existing release pipelines via standard command invocations. Integrating dSYM upload directly into Firebase removes the legacy dependency on the Fabric `run script` Build Phase in Xcode, which is the canonical prerequisite that `EPIC-MIG-10` (Fabric decommission) consumes when it sweeps `fabric.io` references out of every Xcode project. NDK native symbol upload enables symbolicated stack traces for native (C/C++) Android crashes — a capability the legacy Fabric SDK did not support as cleanly, so for many apps this cutover is the FIRST time native crash frames will appear as function names rather than hex addresses; this directly unlocks root-cause diagnosis for segfaults, ABI mismatches, native library bugs, and JNI-boundary failures. Roles that benefit include mobile developers (symbolicated frames in every crash, faster diagnosis), on-call engineers (no manual mapping-file lookups during incident response), release managers (no risk of an unsymbolicated post-cutover release polluting the dashboard), data analysts (clean BigQuery exports with human-readable frames per `EPIC-PA-06`), and the migration program lead (a concrete cutover gate that unblocks `EPIC-MIG-08` historical reconciliation and `EPIC-MIG-10` Fabric decommission).

## In Scope

The following items are included in this epic:

- Cutover of Android ProGuard/R8 mapping file uploads from the legacy 20+ MB Fabric Gradle plugin to the new approximately 100 KB Firebase Crashlytics Gradle plugin, including configuration of the plugin's `mappingFileUploadEnabled` switch (default `true` for release builds) and verification that the canonical Gradle task `uploadCrashlyticsMappingFile<Variant>` is registered for every release variant of every in-scope Android app.
- Integration of iOS dSYM upload into Firebase Crashlytics via the Firebase-provided `${PODS_ROOT}/FirebaseCrashlytics/upload-symbols` Run Script Build Phase (CocoaPods integration), the equivalent SPM-resolved script-path Run Script Build Phase (Swift Package Manager integration), or the `fastlane upload_symbols_to_crashlytics` action where Fastlane is the canonical release pipeline, with verification that the script runs on every release-configuration archive build.
- Cutover of NDK native symbol uploads to Firebase Crashlytics for every in-scope Android app shipping native code, including configuration of the `firebaseCrashlytics { nativeSymbolUploadEnabled true }` extension in the module-level `build.gradle`, configuration of the `unstrippedNativeLibsDir` (or equivalent) so unstripped `.so` files are accessible to the upload task, and registration of the `uploadCrashlyticsSymbolFile<Variant>` task for every release variant.
- CI/CD pipeline updates so that release builds invoke `./gradlew assembleRelease uploadCrashlyticsMappingFile<Variant>` (and `uploadCrashlyticsSymbolFile<Variant>` for NDK builds) on Android, run the Firebase-targeted Run Script Build Phase or `fastlane upload_symbols_to_crashlytics` action on iOS, and surface a non-empty registered-file summary from Firebase in the CI build log so any silent upload failure surfaces immediately.
- Coverage of multi-ABI Android builds (`armeabi-v7a`, `arm64-v8a`, `x86`, `x86_64`) so that NDK symbol files for every shipped ABI are registered separately with Firebase, with verification that the Firebase Console can resolve native frames for crashes from devices of any supported ABI.
- Coverage of Bitcode-enabled iOS apps where App Store Connect recompiles the binary and emits new dSYM files post-upload — the post-recompilation dSYMs are downloaded from App Store Connect (via Xcode → Organizer → Downloads → "Download dSYMs..." or via `fastlane download_dsyms`) and uploaded to Firebase via the same upload script or Fastlane action used by the in-build path.
- Coverage of cross-platform frameworks where the underlying native hosts produce mapping/symbol artifacts that require Firebase upload — Flutter `--obfuscate --split-debug-info` symbol bundles, Unity IL2CPP symbol files per ABI, and React Native source maps produced by the Metro bundler — though the SDK installation that makes these uploads meaningful is the responsibility of `EPIC-MIG-05`.
- Validation that symbolicated stack traces appear in the Firebase Console for at least one representative crash on each in-scope platform after cutover, with the validation crash explicitly distinct from the `EPIC-MIG-09` test-crash validation (this epic checks the symbolication pathway, not the end-to-end pipeline).

## Out of Scope

The following items are explicitly excluded from this epic and are typically owned by a sibling or successor epic:

- Installation of the underlying platform Crashlytics SDKs and Gradle/CocoaPods/SPM dependencies — owned by `EPIC-MIG-03` (Android Gradle plugin classpath, Firebase Crashlytics library, Firebase Android BoM), `EPIC-MIG-04` (iOS CocoaPods `pod 'FirebaseCrashlytics'` or SPM `FirebaseCrashlytics` product), and `EPIC-MIG-05` (FlutterFire `firebase_crashlytics`, Firebase Unity SDK, `@react-native-firebase/crashlytics`). This epic CONSUMES those installed plugins and SDKs to invoke their upload tasks; it does not install them.
- Steady-state symbolication semantics in the pipeline theme — owned by `../pipeline/EPIC-PA-03`. The pipeline epic describes how Firebase Crashlytics' server-side symbolication resolves mapping/symbol artifacts against incoming crash reports; this migration epic describes how the per-app upload pathways are CUT OVER from Fabric to Firebase.
- Removal of legacy Fabric upload jobs, the Fabric `run script` Build Phase in Xcode, the `fabric.yml` configuration file in CI directories, and any remaining `fabric.io` credential references in CI secret management — owned by `EPIC-MIG-10` (Fabric decommission). This epic ADDS the new Firebase-targeted upload steps; the symmetric REMOVAL of the legacy Fabric steps is sequenced into `EPIC-MIG-10` so the rollout is two-phase (add new, validate, then remove old) and dual-running coexistence is preserved during the validation window.
- Test-crash validation that confirms symbolication works end-to-end — owned by `EPIC-MIG-09` (test-crash validation cutover). This epic validates that the upload pathway is correctly wired by triggering at least one representative crash per platform and inspecting the resulting Firebase Console entry; the end-to-end test-crash protocol (force-crash command, cold relaunch, five-minute SLA, dual-running validation window, traffic cutover sign-off) is owned by `EPIC-MIG-09`.
- Historical mapping- and symbol-artifact migration from the legacy Fabric service — owned by `EPIC-MIG-08` (historical data migration). This epic establishes the FORWARD upload pathway for new releases; reconciliation of pre-cutover historical crash data is `EPIC-MIG-08`'s concern.
- Provisioning of the Firebase project and per-app bundle binding — owned by `EPIC-MIG-02`; this epic CONSUMES the resulting `google-services.json` (Android) and `GoogleService-Info.plist` (iOS) configuration files referenced by the upload tasks but does not produce them.
- Inventory of which Android apps ship NDK native code, which iOS apps have Bitcode enabled, and which cross-platform frameworks each app uses — owned by `EPIC-MIG-01` (inventory and readiness); this epic CONSUMES that readiness report to scope the per-app cutover work but does not produce it.

### STORY-MIG-06-S01: Cutover Android ProGuard/R8 mapping uploads to new Crashlytics Gradle plugin

**As a** mobile developer, **I want** Android ProGuard/R8 mapping files uploaded via the new approximately 100 KB Firebase Crashlytics Gradle plugin, **so that** Android stack traces are symbolicated in the Firebase Console and Java/Kotlin frames render as original class and method names rather than as obfuscated tokens.

#### Acceptance Criteria

- **Given** the Android `build.gradle` has the `com.google.firebase.crashlytics` plugin applied (per `EPIC-MIG-03`), **When** a developer runs `./gradlew assembleRelease` on a release variant with minification enabled (`minifyEnabled true`), **Then** the build emits a ProGuard/R8 mapping file at the canonical Gradle output location (`app/build/outputs/mapping/<variant>/mapping.txt`) and no Fabric-related upload command appears in the Gradle task graph.
- **Given** the project has minification enabled, **When** the developer runs `./gradlew uploadCrashlyticsMappingFile<Variant>` (e.g., `uploadCrashlyticsMappingFileRelease`) for a release variant, **Then** the upload completes with a `BUILD SUCCESSFUL` exit status, the Crashlytics Gradle plugin's log output reports the mapping file as registered with the Firebase project, and the per-variant `crashlytics-build.properties` and `crashlytics-buildid.properties` artifacts are generated under `app/build/intermediates/`.
- **Given** a force-crash from a minified release build that was uploaded after its mapping file was registered with Firebase, **When** the developer inspects the crash in the Firebase Console issue card, **Then** the stack trace renders with original class, method, and source-file names (for example, `com.example.app.MainActivity.onCreate(MainActivity.kt:42)`) rather than obfuscated tokens (for example, `a.b.c(d.kt:1)`), and every frame in the user-code portion of the trace is symbolicated.
- **Given** the legacy Fabric mapping-upload step in the CI pipeline (typically a `crashlyticsUploadDeobs<Variant>` or `crashlyticsUploadStoredDeobs<Variant>` task from the legacy plugin), **When** the cutover for this app is complete, **Then** the legacy step is annotated as deprecated in the CI configuration with a TODO referencing `EPIC-MIG-10` for final removal, and the new Firebase upload step runs in its place during the dual-running validation window.

#### Notes

- The new Firebase Crashlytics Gradle plugin is approximately 100 KB versus the legacy 20+ MB Fabric plugin per the Firebase Blog announcement; the footprint reduction is observable on the CI worker as a smaller `~/.gradle/caches/modules-2/files-2.1/com.google.firebase/` footprint compared with the legacy `com.fabric.tools/` cache.
- For DexGuard or other non-standard obfuscators (flagged as risk `R-MIG-02` in the migration theme README), the mapping-file output path differs from the canonical R8 location and the upload procedure may require a custom `firebaseCrashlytics { mappingFile = file("...") }` override; verify against the canonical Firebase Crashlytics troubleshooting documentation and record the override in the per-app readiness entry from `EPIC-MIG-01`.
- The `uploadCrashlyticsMappingFile<Variant>` task is wired into the release build graph automatically by the plugin when `mappingFileUploadEnabled` is `true` (the default for release variants), so most teams will not need to invoke the task explicitly from CI — the `assembleRelease` invocation will trigger it as a dependency.

### STORY-MIG-06-S02: Integrate iOS dSYM upload into Firebase Crashlytics

**As a** mobile developer, **I want** iOS dSYM files uploaded to Firebase Crashlytics as part of every release build, **so that** iOS stack traces are symbolicated in the Firebase Console and Swift/Objective-C frames render as original symbol names rather than as hex memory addresses, with the upload pathway covering both in-build Bitcode-disabled releases and post-recompile Bitcode-enabled releases.

#### Acceptance Criteria

- **Given** an iOS release build (`Release` configuration) produces dSYM files at the canonical archive location (the `.xcarchive` bundle's `dSYMs/` directory), **When** the project's Run Script Build Phase invokes the Firebase upload script (`"${PODS_ROOT}/FirebaseCrashlytics/upload-symbols" -gsp "${PROJECT_DIR}/GoogleService-Info.plist" -p ios "${DWARF_DSYM_FOLDER_PATH}/${DWARF_DSYM_FILE_NAME}"` for CocoaPods integrations, or the equivalent SPM-resolved script path for Swift Package Manager integrations), **Then** the dSYMs are uploaded to Firebase Crashlytics for the bundle identifier resolved from `GoogleService-Info.plist` and the build log shows a successful upload acknowledgement per dSYM file.
- **Given** a force-crash from a release build that was uploaded after its dSYMs were registered with Firebase, **When** the developer inspects the crash in the Firebase Console issue card, **Then** the stack trace renders with symbolicated Swift and Objective-C symbol names (for example, `MyApp.ViewController.viewDidLoad() (ViewController.swift:33)`) rather than hex addresses (for example, `0x10004a2b8`), and every user-code frame above the OS-frame boundary is symbolicated.
- **Given** a Bitcode-enabled build was uploaded to App Store Connect (where Apple recompiles the binary and emits new dSYMs post-recompilation), **When** the developer downloads the recompiled dSYMs from Xcode → Organizer → Downloads → "Download dSYMs..." (or via `fastlane download_dsyms`) and re-runs the Firebase upload command targeting the downloaded dSYM bundle, **Then** the post-Bitcode-recompilation dSYMs are also registered with Firebase Crashlytics and crash reports from devices running the recompiled binary are symbolicated to the same fidelity as the in-build path.
- **Given** the legacy Fabric `run script` Build Phase that invokes the sunset Fabric upload command, **When** the cutover for this app completes, **Then** the new Firebase-targeted Run Script Build Phase is ADDED to the project's Build Phases ordered AFTER the standard build phases but BEFORE any post-archive steps, with the legacy Fabric phase preserved during the dual-running window for `EPIC-MIG-09` validation and annotated for removal by `EPIC-MIG-10`.

#### Notes

- For Bitcode-enabled apps, App Store Connect recompiles the binary on the server side and the original dSYMs uploaded at archive time are insufficient — the recompiled dSYMs must be downloaded after the build is processed and uploaded to Firebase, OR Bitcode must be disabled at the target level to avoid the round-trip. Apple has deprecated Bitcode for new Xcode versions, so this caveat is increasingly historical; nonetheless, projects still shipping with Bitcode enabled must include the post-recompile dSYM download in the release runbook.
- Fastlane provides the `upload_symbols_to_crashlytics` action that wraps the Firebase upload script and accepts a `dsym_path` parameter; teams already using Fastlane for release automation typically prefer this action over a Run Script Build Phase because it integrates with the existing release lane and benefits from Fastlane's parallelism and retry semantics.
- The Firebase upload script is shipped under `${PODS_ROOT}/FirebaseCrashlytics/upload-symbols` for CocoaPods integrations and is resolved via the Firebase iOS SDK SPM package for Swift Package Manager integrations; both produce identical Firebase Console results.

### STORY-MIG-06-S03: Cutover NDK native symbol uploads to Firebase Crashlytics

**As a** mobile developer, **I want** NDK native symbol files uploaded to Firebase Crashlytics for Android apps using native code, **so that** native crashes (segfaults, ABI mismatches, native library bugs, JNI-boundary failures) produce symbolicated stack traces in the Firebase Console rather than hex-address frames, and root-cause diagnosis of native issues becomes practical at the same throughput as Java/Kotlin crash diagnosis.

#### Acceptance Criteria

- **Given** an Android app with native code compiled via the NDK (one or more `.so` libraries shipped under `lib/<abi>/` in the APK or AAB), **When** the developer adds the `firebaseCrashlytics { nativeSymbolUploadEnabled true }` extension to the module-level `build.gradle` and points the `unstrippedNativeLibsDir` (or equivalent ABI-aware setting) at the unstripped `.so` output directory, **Then** the `uploadCrashlyticsSymbolFile<Variant>` task is registered for every release variant and `./gradlew tasks --all` lists it explicitly under the Crashlytics task group.
- **Given** the developer runs `./gradlew uploadCrashlyticsSymbolFile<Variant>` (or `./gradlew assembleRelease` if the task is wired into the release build graph), **When** the upload completes, **Then** the build log reports the unstripped `.so` symbol files as registered with the Firebase project per ABI, and the registered files include one symbol-file entry per `(.so library, ABI)` pair shipped in the build.
- **Given** a force-crash in native code (for example, a deliberate `*((volatile int*)0) = 0xDEAD;` dereference in a JNI function exposed to test code), **When** the developer inspects the crash in the Firebase Console issue card, **Then** the stack trace renders with native function names and source-file/line references (for example, `myNativeFunction (jni_bridge.cpp:127)`) rather than hex addresses (for example, `0x7f2a4b8e10`), and the symbolicated frame chain extends across the JNI boundary into the C/C++ code.
- **Given** the app supports multiple ABIs (`armeabi-v7a`, `arm64-v8a`, `x86`, `x86_64`), **When** the symbol upload task runs, **Then** the unstripped symbol files for each ABI are uploaded separately and registered with Firebase under their respective ABI identifiers, and a crash from a device of any supported ABI resolves to symbolicated frames against the matching ABI-specific symbol file rather than falling back to the wrong ABI's symbols or to hex addresses.

#### Notes

- NDK ABI-specific symbol uploads can be large — a single `.so` library compiled for four ABIs (`armeabi-v7a`, `arm64-v8a`, `x86`, `x86_64`) with debug symbols may total tens of megabytes per release; CI artifact caches and the upload step's network budget may need tuning, and very large symbol bundles benefit from CI runners with more memory headroom for the Gradle upload task.
- The legacy Fabric SDK had less mature NDK support than the new Firebase Crashlytics SDK; for many apps migrating from Fabric, this story marks the FIRST time native crash symbolication is available end-to-end, so it should be framed as an upside of the migration rather than as a cost-equivalent swap. Native crashes that were previously rendered as hex-address-only frames in Fabric will appear with function names and line numbers in the Firebase Console after this cutover completes.
- The `firebaseCrashlytics { nativeSymbolUploadEnabled true }` extension lives in the module-level `build.gradle` and is namespaced under the Crashlytics Gradle plugin DSL; it is wired into the release build graph automatically once enabled, so explicit invocation from CI is optional but recommended for visibility in the build log.

### STORY-MIG-06-S04: Update CI/CD pipelines to use new symbol upload commands

**As a** release manager, **I want** CI/CD pipelines updated to invoke the new Firebase Crashlytics symbol upload commands on every release build, **so that** every shipped artifact automatically registers its mapping and symbol files with Firebase and no manual symbol-upload step or out-of-band runbook task is required at release time.

#### Acceptance Criteria

- **Given** the CI configuration for an Android release build (a GitHub Actions workflow, GitLab CI job, Jenkins pipeline, Bitrise workflow, or equivalent), **When** the release manager inspects the pipeline definition file, **Then** the pipeline invokes `./gradlew assembleRelease uploadCrashlyticsMappingFile<Variant>` (and `uploadCrashlyticsSymbolFile<Variant>` for NDK builds, gated by a per-app boolean from the `EPIC-MIG-01` readiness report) and the legacy Fabric upload commands are annotated as deprecated with a TODO referencing `EPIC-MIG-10`.
- **Given** the CI configuration for an iOS release build, **When** the release manager inspects the pipeline definition file, **Then** the dSYM upload step targets Firebase via the Firebase-provided `upload-symbols` script (CocoaPods or SPM path) or the `fastlane upload_symbols_to_crashlytics` action, and not the legacy Fabric upload script; the Fabric step is preserved during the dual-running validation window and annotated for removal by `EPIC-MIG-10`.
- **Given** a release build runs through CI after the pipeline changes are merged, **When** the build completes, **Then** the CI log shows the symbol upload step succeeded with a non-empty registered-file summary from Firebase (typically a one-line acknowledgement per uploaded artifact reporting the bundle ID and the artifact identifier), and the absence of such a summary surfaces as an explicit CI failure rather than as a silent pass.
- **Given** any historical CI step that targeted the legacy Fabric upload endpoint (for example, `crashlyticsUploadDistribution<Variant>`, the legacy Fabric `run script` Build Phase shell-out, or a custom `fabric_upload` script), **When** the cutover for the corresponding platform completes, **Then** the legacy step is annotated in the CI configuration with a `# DEPRECATED: removal owned by EPIC-MIG-10` comment and is preserved unchanged during the `EPIC-MIG-09` dual-running validation window so a regression in the new pipeline can be diagnosed against an identical legacy baseline.

#### Notes

- The streamlined Gradle plugin API per the Firebase Blog announcement is intentionally simpler than the legacy Fabric configuration; the new commands should reduce CI script complexity rather than increase it. A typical Android release stage shrinks from a multi-task Fabric configuration to a single `./gradlew assembleRelease uploadCrashlyticsMappingFile<Variant>` invocation that triggers mapping and symbol uploads as dependent tasks.
- For engineering environments with strict secret management, any credential material required by the upload step must be supplied through approved CI secret management and must never be logged or echoed in CI output. The specific delivery mechanism for that credential material is intentionally out of scope for this epic; each implementing team selects an approved mechanism that aligns with its organization's secret-management policy.
- Where Fastlane is the canonical release pipeline, the `upload_symbols_to_crashlytics` action accepts a `dsym_path` and a `gsp_path` parameter; teams should pin Fastlane to a version known to be compatible with the current Firebase Crashlytics SDK release line to avoid action-API drift during minor Firebase upgrades.

## Definition of Done

The epic is considered complete when ALL of the following observable conditions are simultaneously true:

- All 4 embedded stories' acceptance criteria are satisfied for every in-scope client app.
- All 5 epic-level acceptance criteria are satisfied across every in-scope platform (Android, iOS, NDK, cross-platform frameworks where applicable).
- The module-level `build.gradle` files of all in-scope Android client apps reference the new Firebase Crashlytics Gradle plugin (applied per `EPIC-MIG-03`) and its mapping-upload task (`uploadCrashlyticsMappingFile<Variant>`) is registered for every release variant; apps shipping NDK native code additionally have the `firebaseCrashlytics { nativeSymbolUploadEnabled true }` extension and the `uploadCrashlyticsSymbolFile<Variant>` task registered.
- The Xcode projects (or `Podfile`/`Package.swift` equivalents) of all in-scope iOS client apps include a Run Script Build Phase that invokes the Firebase Crashlytics `upload-symbols` script with the correct `-gsp` and `-p ios` parameters, OR the `fastlane upload_symbols_to_crashlytics` action is wired into the canonical release lane; Bitcode-enabled apps additionally have a documented post-recompile dSYM download step in the release runbook.
- CI release pipelines for every in-scope client app complete successfully end-to-end with symbol uploads explicitly logged — the Android pipeline emits a Crashlytics-plugin summary line for mapping and symbol uploads, the iOS pipeline emits a Firebase upload-script acknowledgement per uploaded dSYM, and any cross-platform framework's specific upload pathway emits its framework-appropriate confirmation.
- Symbolicated stack traces are visible in the Firebase Console for at least one representative crash on each in-scope platform — Android Java/Kotlin crashes resolve to original class and method names, iOS crashes resolve to Swift/Objective-C symbol names, NDK native crashes resolve to native function names and source-file/line references, and cross-platform framework crashes resolve to their framework-appropriate symbol surfaces (Dart symbols for Flutter, managed C# symbols for Unity, JavaScript stack traces for React Native).
- All legacy Fabric upload steps in every CI pipeline are annotated as deprecated with a comment referencing `EPIC-MIG-10` for final removal and are preserved unchanged during the `EPIC-MIG-09` dual-running validation window so any regression in the new upload pathway can be diagnosed against an identical legacy baseline.
