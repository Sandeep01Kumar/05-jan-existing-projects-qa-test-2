## Description

This epic is CROSS-CUTTING — it does not occupy a specific pipeline stage but rather establishes the privacy and compliance controls that gate the entire crash-reporting pipeline from on-device capture (`EPIC-PA-01`) through dashboard delivery (`EPIC-PA-07`). By default Crashlytics automatically collects crash reports for all an app's users; this epic documents the controls that allow teams to flip that default to opt-in for jurisdictions, app categories, or user populations where the automatic-collection default is inappropriate (notably the EU/EEA under GDPR for certain app categories, certain regulated app categories under CCPA, and any product surface whose privacy posture promises opt-in telemetry). Two complementary opt-out mechanisms anchor the epic: an install-time disable applied via `AndroidManifest.xml` or `Info.plist` (so a build can ship with collection off by default and stay off until the user takes action), and a runtime `setCrashlyticsCollectionEnabled` override that toggles collection on a per-user, per-session basis — including immediate opt-out when a user later revokes consent. Beyond the binary collection toggle, this epic codifies the team's PII redaction policy for what is safe to log via `setCustomKey` and `log` calls (a known foot-gun where well-intentioned developers add useful debugging data that accidentally contains user PII such as names, email addresses, or free-text input), and the team's user-ID handling discipline (use hashed or opaque identifiers in `setUserId` rather than raw emails or usernames). Finally, the epic operationalizes GDPR / CCPA data-subject rights — access, erasure, and portability — across both the Firebase Crashlytics surface and the BigQuery export from `EPIC-PA-06`, so that data-subject requests are operationally answerable rather than aspirational.

## Business Value

Opt-in collection unblocks shipping in jurisdictions where automatic collection is non-compliant — notably the EU/EEA under GDPR for certain app categories and certain CCPA-regulated app categories in California — and prevents the worst-case outcome of a release that collects crash data from users who did not consent and that the team then has to retroactively erase. The runtime `setCrashlyticsCollectionEnabled` override gives apps fine-grained control over collection state: a user who has previously consented can revoke consent at any time in a privacy preferences screen and the app can disable collection immediately for the current session, which is the difference between a privacy posture that survives a consent revocation gracefully and one that requires an app restart or a release cycle to honor the revocation. The PII redaction policy prevents data leaks via custom keys and logs — a class of bug that is easy to commit (a debug `log("user=<raw-email-address>")` call slipped in during local debugging and merged) and hard to detect after the fact (the data has already been uploaded and grouped, and erasing it requires either a BigQuery DELETE or a Firebase erasure request that may not propagate to all downstream copies). The GDPR / CCPA erasure, access, and portability procedures ensure that data-subject rights requests are operationally answerable rather than aspirational — the privacy team has a documented playbook to execute when a request arrives, the playbook covers both Firebase and the BigQuery export from `EPIC-PA-06`, and dry-run executions confirm the playbook actually works before the first real request arrives. Roles that benefit include the security/privacy reviewer (defensible privacy posture for jurisdiction-specific shipping), the mobile developer (clear policy on what is safe to log so the foot-gun is not silently armed), the privacy/legal team member (operational playbook for data-subject requests across Firebase and BigQuery), the mobile end-user (confidence that consent revocations and erasure requests are honored), and the engineering leader (regulatory exposure is bounded by a documented and dry-run-tested compliance posture rather than ad-hoc reactions to individual requests).

## In Scope

The following items are included in this epic:

- Automatic-collection default and the install-time procedure to disable it: setting `firebase_crashlytics_collection_enabled` to `false` via a `<meta-data>` element in `AndroidManifest.xml` on Android, and setting `FirebaseCrashlyticsCollectionEnabled` to `false` in `Info.plist` on iOS. The install-time disable is the canonical safe default for jurisdictions where opt-in is required because it ensures no crash data is collected before the user has affirmatively consented through the app's privacy preferences UI.
- The `setCrashlyticsCollectionEnabled(true|false)` runtime API across all supported client platforms: Android (`FirebaseCrashlytics.getInstance().setCrashlyticsCollectionEnabled(...)` in Java/Kotlin), iOS (`Crashlytics.crashlytics().setCrashlyticsCollectionEnabled(...)` in Swift/Objective-C), Flutter (`FirebaseCrashlytics.instance.setCrashlyticsCollectionEnabled(...)`), and React Native (`crashlytics().setCrashlyticsCollectionEnabled(...)` via `@react-native-firebase/crashlytics`). The runtime override is the user-consent integration point and must propagate immediately to the underlying SDK regardless of what the install-time default was.
- The opt-in collection workflow: gate Crashlytics initialization on a documented consent signal from the user (for example, the user has explicitly granted "crash diagnostics" consent in a privacy preferences screen, or the app has detected a jurisdiction where opt-in is required and the user has affirmatively opted in). The workflow documents the order of operations: first determine consent state, then either enable or disable collection accordingly, then proceed with normal app initialization.
- The PII redaction policy: a documented allowlist of what is safe to log via `setCustomKey` and `log` calls (for example, feature flag values, app state machine states, build variant identifiers, hashed user identifiers) and a documented denylist of what is not safe (for example, raw email addresses, full names, payment data, free-text user input, geolocation precise to a residential address, government identifiers). The policy includes training material so onboarding developers internalize it before their first `setCustomKey` or `log` call.
- User-ID handling discipline: when and how to call `setUserId`, with privacy considerations documented. Specifically, the value passed to `setUserId` must be a hashed or opaque identifier (for example, a SHA-256 hash of an internal account ID, or a randomly generated UUID that the app maps to the user locally) rather than a raw email or username. The discipline includes guidance on when to clear the user ID (for example, on logout) so that subsequent crashes from the same device are not falsely attributed to a logged-out user.
- GDPR / CCPA data-subject rights: documented procedures for access (produce the data subject's crash records), erasure (remove the data subject's crash records), and portability (export the data subject's crash records in a portable format such as JSON or CSV) requests. Each procedure covers both Firebase Crashlytics (via Firebase's documented erasure mechanism) and the BigQuery export from `EPIC-PA-06` (via team-controlled SQL `DELETE` and `SELECT` against the exported tables).
- Data residency awareness: cross-reference to `EPIC-PA-06` for the documented behavior that new BigQuery datasets created via the Crashlytics export are located in the United States regardless of the Firebase project's location, and cross-reference to Firebase Crashlytics' own residency commitments. Teams whose privacy posture requires non-US data residency for the BigQuery export must surface that constraint here and design the procedures accordingly.

## Out of Scope

The following items are explicitly excluded from this epic and are typically owned by a sibling or successor epic:

- SDK capture mechanics (the runtime hooks for unhandled exceptions, NDK signal handlers, ANR detection, and non-fatal `recordError`) — owned by `EPIC-PA-01`. This epic GATES capture (capture must not occur when collection is opted out) but does not own the mechanics themselves; capture defects discovered while validating the privacy gate are referred back to `EPIC-PA-01`.
- SDK transport mechanics (background upload on next launch, post-app-close upload, exponential backoff retries, HTTPS transport security) — owned by `EPIC-PA-02`. This epic GATES transport (transport must not occur when collection is opted out, and locally buffered crashes must be discarded or not uploaded when the user has revoked consent) but does not own the mechanics themselves.
- Durable persistence and BigQuery export linking — the mechanism is owned by `EPIC-PA-06`. This epic CONSUMES the BigQuery export surface to execute erasure and access procedures but does not own the export wiring or the retention horizon; retention policy enforcement is `EPIC-PA-06`'s concern, while the legal and policy framing around what erasure means and when it must be honored is owned here.
- Firebase Console dashboard display, including how a hashed user ID renders on an issue card or how custom-key values are surfaced — owned by `EPIC-PA-07`. This epic's PII redaction policy determines what flows into custom keys and logs, but the actual rendering decisions in the console UI belong to `EPIC-PA-07`.
- Legal counsel and regulatory interpretation — the engineering team partners with legal but does not own legal opinions. This epic operationalizes a privacy posture that legal counsel ratifies; it does not produce a legal opinion on whether a particular jurisdiction requires opt-in for the app's specific category. The annual review cadence in this epic's Definition of Done is the operational touchpoint where legal counsel re-validates the posture.
- Cross-pipeline privacy gates for non-Crashlytics Firebase products (for example, Analytics, Performance Monitoring, Remote Config) — those products have their own collection flags and their own opt-in workflows. This epic confines itself to Crashlytics; cross-product privacy posture is handled by the team's overall privacy program and is referenced here only via the `EPIC-MIG-07` Analytics translation dependency.

## User Stories

This epic contains 4 user stories. Each story is derived from `../templates/story-template.md` and embedded inline below using H3 headings (Rule AR-1). Stories live INSIDE their parent epic file to keep each epic self-contained and eliminate broken cross-file links during refactors. The four stories partition the epic into its two opt-out mechanisms (install-time disable in `STORY-PA-09-S01`, runtime toggle in `STORY-PA-09-S02`), the operational PII hygiene policy that prevents debug-time data leaks (`STORY-PA-09-S03`), and the data-subject rights playbook that operationalizes GDPR / CCPA across Firebase and BigQuery (`STORY-PA-09-S04`).

### STORY-PA-09-S01: Disable automatic Crashlytics collection by default

**As a** security/privacy reviewer, **I want** automatic Crashlytics collection disabled by default in jurisdictions where opt-in consent is required, **so that** the app does not collect crash data before the user has affirmatively consented.

#### Acceptance Criteria

- **Given** an Android app build targeting a jurisdiction where opt-in is required, **When** `AndroidManifest.xml` includes `<meta-data android:name="firebase_crashlytics_collection_enabled" android:value="false" />` inside the `<application>` element, **Then** the SDK does NOT automatically initialize crash collection on app start and no crash payload is uploaded until a runtime override re-enables collection.
- **Given** an iOS app build targeting a jurisdiction where opt-in is required, **When** `Info.plist` includes the `FirebaseCrashlyticsCollectionEnabled` key set to `false` (Boolean), **Then** the SDK does NOT automatically initialize crash collection on app start and no crash payload is uploaded until a runtime override re-enables collection.
- **Given** automatic collection is disabled at install time on either platform, **When** the user later grants consent through the app's privacy preferences UI, **Then** the app can re-enable collection by calling `setCrashlyticsCollectionEnabled(true)` (as covered by `STORY-PA-09-S02`) and the runtime override takes precedence over the install-time default for the remainder of the session and for subsequent sessions until cleared.
- **Given** automatic collection is disabled at install time and no runtime override has been set, **When** a crash occurs and the app cold-relaunches, **Then** the crash is NOT uploaded to Firebase and any locally buffered crash payload from the crashed session is discarded rather than retained for later upload.

#### Notes

- Per Firebase guidance, by default Crashlytics automatically collects crash reports for all an app's users; opt-in reporting requires AFFIRMATIVELY disabling automatic collection via the install-time manifest or plist flag. Teams that ship without this flag are implicitly running in automatic-collection mode regardless of any consent UI the app surfaces, which is the most common privacy posture bug in this area.
- The install-time `false` value provides a safe default for jurisdictions where opt-in is required because it eliminates the race condition between SDK initialization and the user's consent decision: the SDK simply does not collect until told to, so even a first-launch crash before the consent UI has displayed is uncollected rather than collected and later erased.
- The install-time disable is a per-build decision; teams that ship the same APK or IPA across multiple jurisdictions and want jurisdiction-specific behavior must combine the install-time disable (so the default is the conservative opt-in posture) with a runtime decision (so users in jurisdictions where opt-out is acceptable can be opted in via `STORY-PA-09-S02` based on the detected jurisdiction).

### STORY-PA-09-S02: Toggle collection at runtime via setCrashlyticsCollectionEnabled

**As a** mobile developer, **I want** to toggle Crashlytics collection at runtime via `setCrashlyticsCollectionEnabled`, **so that** I can respect the user's current consent choice on each session — including immediate opt-out when the user revokes consent in the app's privacy preferences UI.

#### Acceptance Criteria

- **Given** an Android app that has called `FirebaseCrashlytics.getInstance().setCrashlyticsCollectionEnabled(true)` during initialization after detecting user consent, **When** a crash occurs and the app cold-relaunches, **Then** the crash is captured by `EPIC-PA-01` mechanisms and uploaded via `EPIC-PA-02` transport, and the resulting issue card is visible in the Firebase Console per `EPIC-PA-07`.
- **Given** the runtime override is set to `false` on any supported platform, **When** a crash occurs and the app cold-relaunches, **Then** the crash is NOT uploaded to Firebase, the locally buffered payload (if any) is discarded, and no issue card appears in the Firebase Console for the crash.
- **Given** a user has previously consented and later revokes consent in the app's privacy preferences screen, **When** the app calls `setCrashlyticsCollectionEnabled(false)` in response to the revocation, **Then** collection stops immediately for the current session, the override is persisted across app launches, and the user's subsequent crashes are not collected unless and until the user grants consent again.
- **Given** a Flutter app, **When** the developer calls `FirebaseCrashlytics.instance.setCrashlyticsCollectionEnabled(false)`, **Then** the override propagates to the underlying Android or iOS native SDK and collection stops on whichever platform the app is running on; the override behaves identically to a direct native call on each platform.
- **Given** a React Native app using `@react-native-firebase/crashlytics`, **When** the developer calls `crashlytics().setCrashlyticsCollectionEnabled(false)`, **Then** the override propagates to the underlying Android or iOS native SDK and collection stops on whichever platform the app is running on; the override behaves identically to a direct native call on each platform.

#### Notes

- Per Firebase guidance, the data-collection override can be set to `false` to opt out. Runtime toggling is the user-consent integration point — surface the toggle prominently in the privacy preferences UI rather than burying it behind a sub-menu so users can locate and exercise their consent choice without friction.
- Runtime toggling complements the install-time disable from `STORY-PA-09-S01` rather than replacing it. The recommended pattern is: install-time disable on (conservative default), then runtime enable on consent (so users in opt-out jurisdictions can be enabled, and users in opt-in jurisdictions are enabled only after affirmative consent). This pattern is robust against both first-launch crashes (covered by install-time disable) and consent-revocation events (covered by runtime toggle).
- The override should be considered authoritative for the lifetime of the app session; do not re-read consent state during a session in a way that could race against an in-flight crash upload. If the user revokes consent mid-session, the override is toggled and any future crashes from that session are not collected, but the app should not retroactively erase already-uploaded crashes — that is a job for the erasure procedure in `STORY-PA-09-S04`.

### STORY-PA-09-S03: Enforce PII redaction policy for custom keys and logs

**As a** security/privacy reviewer, **I want** a documented PII redaction policy with developer training and code-review enforcement, **so that** developers do not accidentally leak PII via `setCustomKey` or `log` calls into crash reports that are then uploaded to Firebase and the BigQuery export.

#### Acceptance Criteria

- **Given** a documented PII redaction policy committed to the team's internal documentation surface, **When** the team trains developers, **Then** the policy lists EXAMPLES of what is safe to log (for example, feature flag values, app state machine states, build variant identifiers, hashed user identifiers) AND examples of what is NOT safe (for example, raw email addresses, full names, payment data, free-text user input, geolocation precise to a residential address, government identifiers), and the training includes a worked exercise of identifying which `setCustomKey` and `log` calls would violate the policy.
- **Given** the policy mandates hashing of identifiers, **When** developers call `setUserId`, **Then** they pass a hashed or opaque identifier (for example, a SHA-256 hash of an internal account ID, or a randomly generated UUID that the app maps to the user locally) rather than a raw email, username, or phone number; the policy includes a documented hashing approach so all teams use the same scheme and identifiers are correlatable across teams.
- **Given** developer-authored `log("...")` calls and `setCustomKey("...", value)` calls appear in code review, **When** the reviewer evaluates them, **Then** the reviewer confirms that the log string and the custom-key value do not contain PII per the policy, and any violation blocks the pull request until the offending call is redacted or removed; a comment template referencing this story by ID makes review feedback consistent across reviewers.
- **Given** the policy is documented in a discoverable internal location, **When** new developers join the team, **Then** onboarding includes a review of this policy as a required item before the developer's first commit that touches Crashlytics instrumentation, and onboarding completion is recorded so the team can audit which developers have been trained.

#### Notes

- Per industry guidance, compliance with GDPR and CCPA requires avoiding the logging of user PII; data should be anonymized using hashed IDs or generic labels; and teams should be trained on what is safe to log. This story operationalizes that guidance by combining a written policy (so the rules are durable and reviewable), training (so new developers internalize them), and code review (so the rules are enforced in practice).
- The policy is operationalized via code review because automated linting can catch only the simplest mistakes — for example, a literal `@` character in a `log` string suggests an email, but a `log("user=" + userObject.toString())` whose `toString()` returns an email is not detectable by a regex. Code review remains the primary control; automated linting is a useful secondary check but is not a substitute.
- The policy applies to BOTH `setCustomKey` and `log` calls because both flow into the crash payload that is uploaded and then made available in the Firebase Console issue card and the BigQuery export. A leak via either path has the same downstream consequence and the same erasure burden.

### STORY-PA-09-S04: Operationalize GDPR / CCPA data-subject rights

**As a** privacy/legal team member, **I want** documented procedures for honoring data-subject access, erasure, and portability requests across Firebase Crashlytics and the BigQuery export, **so that** GDPR and CCPA obligations are operationally answerable within the team's documented response window rather than aspirational claims that have never been exercised end-to-end.

#### Acceptance Criteria

- **Given** a documented data-subject access request procedure and an inbound access request identifying a data subject by the team's user identifier (hashed per the policy from `STORY-PA-09-S03`), **When** the privacy team executes the procedure, **Then** they can produce the data subject's crash records from BOTH the Firebase Crashlytics surface (via Firebase's documented data export mechanism) AND the BigQuery export from `EPIC-PA-06` (via team-controlled SQL `SELECT` against the exported tables filtered by the identifier), and the combined output is delivered to the data subject within the team's documented response window (for example, 30 days for GDPR, 45 days for CCPA).
- **Given** an erasure (Right to be Forgotten) request, **When** the privacy team executes the procedure, **Then** the data subject's records are erased from Firebase Crashlytics (per Firebase's documented procedures) AND from the BigQuery export (via team-controlled SQL `DELETE` against the exported tables filtered by the identifier), the erasure is recorded in the team's audit log, and a follow-up access query confirms no records remain in either surface after the erasure window.
- **Given** a portability request, **When** the privacy team executes the procedure, **Then** the data subject's records are exported in a portable format (for example, JSON or CSV) that includes the crash timestamps, the stack trace summaries (with PII fields blanked per the redaction policy), and the custom-key values associated with each crash, and the export is delivered through a secure channel rather than over insecure email.
- **Given** the access, erasure, and portability procedures are documented and reviewed by legal counsel, **When** the documentation is published to the team's internal documentation surface, **Then** it is discoverable by the privacy team via the team's index, it includes a documented owner for each procedure, and the review cadence (annual at minimum) is recorded so the procedures stay current with both Firebase's evolving capabilities and any regulatory updates.

#### Notes

- Erasure interacts tightly with `EPIC-PA-06` retention — an erasure that ignores the BigQuery export is incomplete because the data continues to exist in the team-owned BigQuery dataset even after Firebase has erased its copy. The procedure documented by this story must propagate erasure to BOTH surfaces; a dry-run that erases only from Firebase and then queries BigQuery to confirm the record still exists demonstrates this point concretely during onboarding.
- Annual review aligns with most regulatory expectations for policy currency. Reviews should specifically check that (a) Firebase's documented erasure mechanism has not changed in a way that invalidates the procedure, (b) the BigQuery schema for the Crashlytics export has not changed in a way that the SQL `DELETE` no longer matches, and (c) the team's user-identifier scheme from `STORY-PA-09-S03` is still the canonical key used to filter records.
- At least one dry-run execution of each procedure is required by the Definition of Done because procedures that have never been exercised end-to-end are almost always wrong in subtle ways (missing tables, mis-typed identifiers, permissions gaps). The dry-run is performed against a synthetic data subject (a test account whose data was generated specifically for the dry-run) so no real user data is affected, and the dry-run outcome is recorded so the team can demonstrate operational readiness to legal counsel and to external auditors if required.


## Acceptance Criteria (Epic-Level)

The following Given-When-Then criteria summarize exit conditions across all stories in this epic (Rule AR-4). They satisfy the user's R-2 directive ("epics with acceptance criteria") and are applied symmetrically with the migration theme for catalog uniformity. This epic carries 5 epic-level acceptance criteria so that the cross-cutting privacy gate is unambiguously specified across both opt-out mechanisms, the PII policy, and the data-subject rights playbook.

- **Given** an app shipped in a jurisdiction where opt-in consent is required, **When** the app starts before the user has interacted with the privacy preferences UI, **Then** Crashlytics automatic collection is disabled (via the `AndroidManifest.xml` `firebase_crashlytics_collection_enabled=false` `<meta-data>` element on Android or the `FirebaseCrashlyticsCollectionEnabled=false` key in `Info.plist` on iOS) and no crash payload is uploaded until a runtime override re-enables collection.
- **Given** the runtime override `setCrashlyticsCollectionEnabled(true|false)` is exposed on all four supported client platforms (Android, iOS, Flutter, React Native), **When** the app calls it in response to the user's consent or revocation, **Then** collection toggles on or off accordingly within the current session, the override propagates to the underlying native SDK on cross-platform runtimes, and any crashes that occur while the override is `false` are not uploaded to Firebase.
- **Given** the team's documented PII redaction policy from `STORY-PA-09-S03`, **When** developers add `setCustomKey`, `log`, or `setUserId` calls anywhere in the codebase, **Then** the calls comply with the policy (no raw PII, hashed or opaque identifiers only) and code review enforces compliance such that violations block the pull request and are recorded in the review history.
- **Given** a GDPR or CCPA data-subject request for access, erasure, or portability identifying a data subject by the team's user identifier scheme, **When** the privacy team executes the documented procedure from `STORY-PA-09-S04`, **Then** the request is fulfilled within the team's documented response window across BOTH Firebase Crashlytics and the BigQuery export from `EPIC-PA-06`, and the execution is recorded in the team's audit log.
- **Given** the documented privacy posture covering install-time disable, runtime toggle, PII redaction policy, and data-subject rights procedures, **When** legal counsel reviews the posture at the documented annual cadence, **Then** the documentation is current, the procedures still work against the current Firebase and BigQuery surfaces, and any drift (changes to Firebase's erasure mechanism, changes to the BigQuery schema, changes to the team's identifier scheme) is reconciled before the review is signed off.

## Definition of Done

The epic is considered complete when ALL of the following observable conditions are simultaneously true:

- All 4 embedded stories (`STORY-PA-09-S01`, `STORY-PA-09-S02`, `STORY-PA-09-S03`, `STORY-PA-09-S04`) have their acceptance criteria satisfied and the satisfaction is recorded in the catalog's traceability surface.
- All 5 epic-level acceptance criteria above are satisfied.
- At least one client app per supported platform (Android, iOS, Flutter, React Native) has automatic collection disabled by default in a relevant jurisdiction-specific build variant, demonstrated by a build configuration audit that shows the `AndroidManifest.xml` `firebase_crashlytics_collection_enabled=false` `<meta-data>` element on Android, the `FirebaseCrashlyticsCollectionEnabled=false` key in `Info.plist` on iOS, and the equivalent native-side configuration for Flutter and React Native.
- The runtime `setCrashlyticsCollectionEnabled` API is exercised in a test that toggles it `false` → `true` → `false` on at least one platform and confirms via the Firebase Console that a force-crashed payload is uploaded only when the override is `true`; the test is repeatable and is documented in the team's test runbook.
- The PII redaction policy from `STORY-PA-09-S03` is documented in an accessible internal location, reviewed by privacy/legal, and referenced from the team's code-review checklist so reviewers can apply it consistently.
- Procedures for GDPR / CCPA access, erasure, and portability from `STORY-PA-09-S04` are documented and dry-run executed at least once against a synthetic test data subject; the dry-run outcomes (records produced, records erased, records exported in portable format) are recorded so the team can demonstrate operational readiness.
- An annual review schedule is established for the privacy posture documentation, with named owners and a documented review checklist that covers Firebase mechanism drift, BigQuery schema drift, and identifier-scheme drift.
- A cross-reference from this epic to `EPIC-MIG-07` Analytics Event Translation is in place documenting how user-ID handling discipline carries over from Crashlytics into Google Analytics for Firebase, so the privacy posture is consistent across both products rather than divergent.
